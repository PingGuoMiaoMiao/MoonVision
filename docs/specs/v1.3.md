# MoonVision v1.3 Spec

## Status

- Phase: approved
- Base branch: `v1.2`
- Goal: refine MoonVision contour analysis from region-level tracing into boundary-level contour hierarchy, while keeping the library within the lightweight `imgproc` scope

## Why v1.3

`v1.2` added `Canny`, ordered contour walks, contour statistics, and upgraded demos.

The current contour layer is usable for:

- one contour per connected foreground region
- ordered boundary traversal on solid regions
- basic contour statistics for demos

But `v1.2` still has an explicit semantic limit:

- hollow foreground is treated as one traced region
- inner holes are not emitted as separate contours
- `find_contours` is still closer to region tracing than to boundary hierarchy

The next iteration should close that gap without expanding into unrelated image-processing areas.

`v1.3` is therefore defined as a contour-semantic refinement release, not a broad feature dump.

It is intentionally **not** the release for:

- interpolation upgrades
- border-mode unification
- affine / perspective transform
- histogram equalization
- contour approximation or shape descriptors

Those are follow-up version lines after contour hierarchy is stable.

## Scope

### In Scope

1. Boundary-level contour output
- `find_contours(binary_image, connectivity?)` returns one contour per traced boundary, not one contour per connected foreground region

2. Contour hierarchy metadata
- each contour carries whether it is an outer contour or a hole contour
- each contour may reference its parent contour when a parent-child relationship exists

3. Contour API clarification
- keep ordered point output
- keep bounding-box access
- clarify the meaning of contour area and perimeter when holes exist
- keep `GrayImage` as the only contour input type

4. Regression-safe compatibility
- solid-region behavior remains stable
- hollow-region behavior becomes explicit and testable

5. Demo and docs updates
- update `object_counting` reporting so contour counts are described as outer/hole-aware contour analysis instead of pure traced-region counts
- update `README` with `v1.2` vs `v1.3` contour semantics

6. Test fixture strengthening
- add hollow and nested contour fixtures directly into focused component tests
- keep fixture scope minimal and tied to contour hierarchy verification

### Out of Scope

- convex hull
- polygon approximation
- contour moments
- shape matching
- border type enums
- interpolation enums
- perspective transform
- histogram equalization
- affine transform
- RGB contour input
- video, GUI, OpenCV bindings, DNN, ML

## API Direction

Follow the current MoonVision style:

- pure functions first
- binary `GrayImage` remains the only contour input type
- deterministic output ordering
- explicit metadata instead of hidden heuristics

Proposed public API additions:

```moonbit
pub enum ContourKind {
  Outer
  Hole
}

pub fn find_contours(
  image : GrayImage,
  connectivity? : Int = 8
) -> Array[Contour]!MoonVisionError

pub fn contour_kind(contour : Contour) -> ContourKind
pub fn contour_parent_index(contour : Contour) -> Int?
pub fn contour_area(contour : Contour) -> Int
pub fn contour_perimeter(contour : Contour) -> Int
pub fn contour_bbox(contour : Contour) -> BoundingBox
```

Direction constraints:

- `find_contours` stays as the primary entrypoint; `v1.3` does not add a second parallel high-level API
- contour order must be deterministic so test snapshots stay stable
- parent contour must appear earlier than child hole contour in returned output
- `contour_area` remains an absolute area value; hole-vs-outer meaning is carried by `ContourKind`, not by signed area in `v1.3`
- `v1.3` does not introduce OpenCV-style retrieval-mode or approximation-mode enums yet; it only establishes hierarchy-correct contour output

## Design Constraints

- stay inside the existing `components` package
- do not redesign `GrayImage`, `RgbImage`, or the repository error model
- do not split contour work into a large new submodule tree in this iteration
- avoid introducing contour approximation or shape descriptors in the same pass
- keep `v1.3` focused on contour semantics, hierarchy, and verification
- do not use `v1.3` to introduce general `BorderType` or `Interpolation` APIs; those belong to later transform/filter specs

## Preparation Notes

Research against OpenCV `imgproc` shows that MoonVision still needs broader mid-layer capabilities such as:

- border-mode unification
- interpolation modes
- shape descriptors
- geometric rectification
- histogram enhancement

Those are real gaps, but they are not `v1.3` work items.

The only preparation items that are allowed to influence `v1.3` are:

- defining exact `outer` / `hole` terminology
- fixing deterministic contour ordering rules
- adding hollow and nested test fixtures
- keeping object count and contour count clearly separated in demo reports

## Behavioral Contract

`v1.3` changes contour semantics in exactly one major way:

- `v1.2`: one contour per connected foreground region
- `v1.3`: one contour per traced boundary, with outer/hole classification

Expected consequences:

- solid shapes still return one contour
- hollow shapes return at least two contours when an outer ring and one enclosed hole are both present
- nested structures may produce more than two contours, with explicit parent references
- contour count in demos may increase on assets that contain holes, even when connected-component count does not change

## Risks

1. API-semantics break on hollow regions
- Existing `v1.2` behavior on hollow regions is intentionally replaced
- Mitigation: document the change explicitly and add direct regression tests for both `v1.2` and `v1.3` semantics

2. Parent-child ordering instability
- If hierarchy order is not deterministic, tests and reports become noisy
- Mitigation: define scan-order based contour discovery and require parent-before-child output

3. Area/perimeter ambiguity
- Hole contours can be misunderstood if area semantics are not stated precisely
- Mitigation: keep area absolute, expose `ContourKind`, and document examples

4. Demo overclaim
- Reporting "more contours" can be confused with "more objects"
- Mitigation: keep component count and contour count as separate metrics in reports

5. Scope creep
- Once contour hierarchy lands, it is tempting to add approximation, hull, or shape descriptors
- Mitigation: keep those explicitly out of scope for `v1.3`

## Validation

Required checks for implementation approval:

- `moon check`
- `moon test`
- `moon run src/demo/object_counting`
- `moon run src/demo/edge_detection`

Required test additions:

- solid square still yields one outer contour
- thin-line contour order remains deterministic
- hollow rectangle yields one outer contour and one hole contour
- nested-hole fixture reports correct parent index relationships
- contour area/perimeter remain stable on simple fixtures after the hierarchy change
- object-counting demo wording remains correct when contour count and component count differ

Documentation checks:

- `README` states the `v1.2` vs `v1.3` contour semantic change
- `object_counting` report text separates detected objects from contour hierarchy output

## Acceptance Criteria

`v1.3` is complete when all of the following are true:

1. `find_contours` returns boundary-level contours with hierarchy metadata
2. Hollow-region fixtures produce separate outer and hole contours
3. Nested-hole fixtures produce deterministic parent-before-child contour ordering
4. `moon test` passes on the repository default target
5. `object_counting` demo runs and reports component count separately from contour hierarchy information
6. `README` documents the `v1.3` contour-hierarchy behavior
7. No feature outside the contour-semantic scope is added in the same iteration

## Commit Strategy

Target 5 to 8 meaningful commits for `v1.3`, for example:

1. add `v1.3` spec and boundary rules
2. refactor contour discovery for outer/hole separation
3. add contour hierarchy metadata and focused tests
4. stabilize contour area/perimeter semantics with regression tests
5. upgrade `object_counting` report wording and outputs
6. update `README` with `v1.2` vs `v1.3` contour comparison
7. run final verification and fix any semantic drift
8. optional final commit only for small wording or deterministic-order corrections discovered during verification

Recommended execution rule:

- each commit must keep contour semantics reviewable
- keep tests in the same commit as the semantic change they validate
- do not mix hierarchy work with unrelated image-processing features
- preserve demo runnability throughout the iteration whenever possible
