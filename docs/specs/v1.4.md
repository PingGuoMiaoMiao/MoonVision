# MoonVision v1.4 Spec

## Status

- Phase: draft
- Base branch: `v1.3`
- Goal: extend MoonVision from contour hierarchy into lightweight shape analysis, while staying inside the small `imgproc` lane

## Why v1.4

`v1.3` established:

- boundary-level contour output
- outer / hole contour classification
- deterministic parent-child hierarchy

That gives MoonVision a usable contour layer, but not yet a usable **shape-analysis layer**.

The next natural step, aligned with the OpenCV `imgproc` shape family, is to add:

- contour simplification
- convex hull
- oriented rectangle fitting
- a small set of derived shape descriptors

`v1.4` is therefore defined as a **shape-analysis refinement release**, not a geometry-transform release and not a histogram-enhancement release.

It is intentionally **not** the release for:

- affine / perspective transform
- interpolation upgrades
- histogram equalization / CLAHE
- Scharr / Laplacian
- connected-components stats expansion

Those belong to later version lines.

## Scope

### In Scope

1. Contour approximation
- add polygonal contour simplification for binary contour point sequences
- keep deterministic output ordering
- first version only needs one approximation strategy

2. Convex hull
- add convex hull extraction from contour point sets
- support concave foreground shapes

3. Minimum-area rotated rectangle
- add oriented rectangle fitting for contour point sets
- keep axis-aligned rectangles stable

4. Basic shape descriptors
- add a minimal descriptor layer derived from existing contour / hull / bbox data
- keep descriptor count intentionally small

5. Demo and docs updates
- update `object_counting` reporting to include at least one simplified contour or shape-summary metric
- update `README` with `v1.3` vs `v1.4` shape-analysis additions

### Out of Scope

- contour retrieval modes
- contour approximation mode families
- Hu moments
- shape matching
- ellipse fitting
- line fitting
- affine transform
- perspective transform
- histogram equalization
- CLAHE
- `BorderType`
- `Interpolation`
- RGB contour input
- video, GUI, OpenCV bindings, DNN, ML

## API Direction

Follow the current MoonVision style:

- pure functions first
- contour inputs stay based on `Contour` or `Array[Point]`
- deterministic output
- no parallel high-level API family in the same release

Proposed public API additions:

```moonbit
pub fn approx_contour(contour : Contour, epsilon : Double) -> Array[Point]

pub fn convex_hull(contour : Contour) -> Array[Point]

pub struct RotatedRect {
  center_x : Double
  center_y : Double
  width : Double
  height : Double
  angle_deg : Double
}

pub fn min_area_rect(contour : Contour) -> RotatedRect

pub fn contour_vertex_count(contour : Contour) -> Int
pub fn contour_circularity(contour : Contour) -> Double
pub fn contour_solidity(contour : Contour) -> Double
```

Direction constraints:

- `epsilon` must be explicit; `v1.4` does not hide approximation tolerance behind magic defaults
- `convex_hull` output order must be deterministic
- `min_area_rect` must be stable on axis-aligned rectangles and simple diamonds
- descriptor semantics must be documented precisely enough for test assertions
- descriptor count stays minimal; `v1.4` does not try to copy the full OpenCV shape-descriptor surface

## Design Constraints

- stay inside the existing `components` package unless readability clearly collapses
- do not redesign `Contour`, `GrayImage`, or repository-wide error handling
- do not add transform-related public types in `v1.4`
- do not add more than one contour-approximation algorithm in this release
- keep `v1.4` focused on shape analysis above the contour layer

## Preparation Notes

The OpenCV comparison work already showed three mid-layer priorities after contour hierarchy:

- contour approximation
- convex hull / oriented rectangle
- shape descriptors

`v1.4` only takes the first stable slice of that layer.

Allowed preparation items for `v1.4`:

- define exact `epsilon` semantics for contour approximation
- define deterministic hull ordering
- define `RotatedRect` field semantics
- add small concave and diamond fixtures for focused tests

Not allowed in `v1.4`:

- turning this into a generic geometry module
- bundling transform / interpolation work into the same pass

## Behavioral Contract

`v1.4` changes MoonVision in one major way:

- `v1.3` stops at contour hierarchy
- `v1.4` allows contour hierarchy output to feed simple shape-analysis operators

Expected consequences:

- rectangle-like shapes can be simplified into small vertex sets
- concave shapes can be summarized by a convex hull
- oriented shape bounds can differ from axis-aligned `BoundingBox`
- object-counting reports can include shape metrics without changing connected-component counts

## Risks

1. Approximation instability
- Small changes in `epsilon` can drastically change vertex count
- Mitigation: keep `epsilon` explicit and test on fixed fixtures

2. Hull ordering ambiguity
- A correct hull with unstable point order is still noisy for tests and demos
- Mitigation: lock deterministic ordering, for example scan-derived start and consistent walk direction

3. Rotated rectangle precision drift
- Floating-point geometry can be fragile on tiny pixel fixtures
- Mitigation: use tolerance-based assertions for non-axis-aligned cases and exact assertions for axis-aligned cases

4. Descriptor overexpansion
- It is easy to keep adding more shape numbers once the descriptor layer exists
- Mitigation: cap `v1.4` at a very small descriptor set

5. Demo overclaim
- Shape-analysis metrics can be confused with object-detection quality improvements
- Mitigation: keep object count and shape summary clearly separated in reports

## Validation

Required checks for implementation approval:

- `moon check`
- `moon test`
- `moon run src/demo/object_counting`
- `moon run src/demo/edge_detection`

Required test additions:

- contour approximation reduces a solid rectangle contour to four stable corners under a suitable `epsilon`
- convex hull removes a concave notch on a fixed binary shape
- `min_area_rect` matches axis-aligned rectangle geometry on a simple box fixture
- `min_area_rect` returns a stable non-zero angle on a small diamond-like fixture, using tolerance-based assertions
- shape descriptors remain finite and stable on fixed fixtures

Documentation checks:

- `README` states the `v1.3` vs `v1.4` shape-analysis change
- `object_counting` report wording keeps object count separate from shape metrics

## Acceptance Criteria

`v1.4` is complete when all of the following are true:

1. contour approximation is implemented and covered by focused tests
2. convex hull is implemented and covered by focused tests
3. `min_area_rect` is implemented and validated on at least one axis-aligned and one rotated-style fixture
4. at least one small descriptor layer is available and tested
5. `moon test` passes on the repository default target
6. `object_counting` demo runs and reports shape-analysis information without conflating it with object count
7. no feature outside the shape-analysis scope is added in the same iteration

## Commit Strategy

Target 5 to 8 meaningful commits for `v1.4`, for example:

1. add `v1.4` spec and fixture rules
2. add contour approximation with focused tests
3. add convex hull with focused tests
4. add rotated rectangle fitting with focused tests
5. add small descriptor helpers and verification
6. update `object_counting` reporting
7. update `README` with `v1.3` vs `v1.4`
8. run final verification and fix deterministic-output drift

Recommended execution rule:

- each commit must add one coherent shape-analysis capability
- keep tests in the same commit as the feature they validate
- do not mix transform work into this release
- preserve `v1.3` contour hierarchy semantics while adding `v1.4` analysis functions
